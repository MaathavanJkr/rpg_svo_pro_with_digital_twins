## Design decisions recorded during execution
- **Main comparison (D4):** M3 publishes information in the same heuristic convention as M2 (normalised ∇D used as the normal). **Ablation:** Hessian-based covariance for both M2 and M3 → 2×2 design {M2, M3} × {heuristic, Hessian}.
- **Initial alignment (D1):** one-time 4-DoF GT alignment at the first keyframe after backend initialisation (see `docs/frames.md`). `refine_T_WL: false` in the main runs; refinement is an ablation.
- **Logging additions (Phases 5, 6, 9):** per keyframe, (i) registration result published vs accepted by the backend (the 1 ms KF stamp match), (ii) registration runtime, (iii) local-cloud point count before/after filtering, (iv) accept/reject with reason.
- **Phase 10 experiment: initial alignment robustness (supports H1).** Inject yaw offsets {0, 2, 5, 10}° into the D1(B) alignment (T_M_W ← R_z(δ)·T_M_W) and run M2 and M3 with `refine_T_WL` off and on (2 × 2 × 4 conditions). Report registration acceptance, ICP correction size, map-frame ATE and whether/when the yaw error is corrected.
- **D1 amended to D1(B) (2026-10-23):** alignment from GT positions over the first L = 2 m of flight; GT orientation not used (docs/frames.md).
- **Statistics (decision 2026-10-23):** all key M1/M2/M3 comparisons report mean ± std (sample std) and Welch's t-test p-values (`analysis/compare_methods.py`).
- **Phase 8 implementation (decided 2026-10-24):** C++ library + pybind11 module `fyp_df` (svo_registration/df_cpp), called from `online_registration_m3.py`, a copy of the M2 node that differs only in the registration step (`registration_method: point_to_plane | distance_field`). The solver is a line-by-line port of the Phase 7 prototype (Eigen LM with the prototype's damping and stopping criteria, Huber IRLS), **not Ceres** as first planned: Ceres' trust-region strategy would not reproduce the prototype's iterates, and the Phase 8 acceptance test is equality with the prototype. Built standalone with plain `-O3` (no `-ffast-math`, unlike SVO). Configuration: unsigned, untruncated, v = 0.05 m, Huber δ = 0.05, 100-iteration cap; information = M2 heuristic with normalised ∇D (main), Hessian (D4 ablation option).
- **H2 timing protocol (decided 2026-10-24, Phase 8):** offline, one process pinned to one core, `OMP_NUM_THREADS=1`, same inputs (the 922 logged V1_01 keyframes), same machine, methods interleaved per keyframe. (a) Core solve: Open3D `registration_icp` as configured in M2 (includes its internal KD-tree build of the target; the build is also timed alone) vs the C++ DF call. (b) End-to-end per-KF node callback for both node paths. Medians and p90; memory = RSS increase from loading the grid vs the twin + KD-tree. Online CPU in Phase 9 is reported separately (Open3D is multi-threaded there).
- **Phase 10 item, H4 city scale (added 2026-10-24):** extrapolate grid memory to the Oerlikon twin's bounding volume at v = 0.05 / 0.10 / 0.20 m, dense (n_x·n_y·n_z·4 B) vs a sparse estimate (only blocks within the truncation band / a narrow band around the surface, e.g. 8³ voxel blocks as in Voxblox/OpenVDB, counted from the twin's occupied blocks). Compare with Oerlikon's point cloud + KD-tree size. Report wording for room scale (Phase 8): "At room scale the DF grid (23 MB, v = 0.05 m) is comparable to and slightly smaller than P2P's map + KD-tree (~36 MB). Memory grows with volume × (1/v)³; city-scale extrapolation and sparse storage are Phase 10."
- **Future work (recorded 2026-10-24): map-based re-alignment after an SVO reset (option (c)).** After a full SVO reset (`resetBackend`) the VIO frame's heading is re-initialised and the one-shot D1 alignment is lost, so map-frame output stops (V1_03, docs/phase6_logging.md). A re-alignment from the registration itself (e.g. re-running the 4-DoF alignment on registered positions after a reset, similar to the original `refine_T_WL` path) would remove this limitation without using GT again. Not implemented; SVO settings are not changed (option (d) rejected).

## Sequences and reset rule (decided 2026-10-24, before Phase 9)
- **Main table (M1/M2/M3):** V1_01_easy, V1_02_medium, V2_02_medium, V2_03_difficult.
- **Excluded:** V1_03_difficult (SVO full resets at ~12.3 s in every run and mid/late-flight resets in 4/5; reported as a limitation, docs/sequence_survey.md and docs/phase6_logging.md).
- **Deferred:** V2_01_easy (early reset at 6.9 s; would need a re-alignment hook after resets within the first 15 s). **Optional, only if time allows after Phase 9.**
- **Pre-registered reset rule (applies to every run of the included sequences, all methods):** a run in which SVO performs a full reset (stage Relocalization → Paused, i.e. `resetBackend`) is a **failure for that method**. Failure counts are reported per method and sequence; failed runs are **excluded from ATE / RPE / drift statistics**; **no re-running until a run passes** (the planned number of runs per method and sequence is executed once; failures are not replaced). Detection: the frame-event log (`log_frame_events:=true`, always on in Phase 9), `analysis/reset_survey.py`.

## Phase 9 pre-registration (written 2026-10-24, BEFORE any Phase 9 run)
- **Build (frozen):** the commit that adds this section is the Phase 9 build. `analysis/run_phase9.sh freeze` writes `runs/phase9/build_freeze.txt` (git hash + md5 of svo_node, libsvo_ros.so, the `fyp_df` module, both registration nodes, the four registration configs, the three launch files, the SVO param files, the harness and batch driver, both twins and both grids). Before **every** run the batch driver recomputes these checksums and aborts on any difference. No code changes during Phase 9. svo_node / libsvo_ros are the binaries used since Phase 6 (no C++ source change since e6848f3). If the smoke run reveals a defect, the fix and a re-freeze happen before the first batch run and are documented; nothing changes after the batch starts.
- **Sequences:** V1_01_easy, V1_02_medium, V2_02_medium, V2_03_difficult. Registration configs: V1 `euroc_v1.yaml` (M2) / `euroc_v1_m3.yaml` (M3), V2 `euroc_v2.yaml` / `euroc_v2_m3.yaml` (values identical to V1; only the twin md5 differs), twins `V{1,2}_leica_v30mm.ply`, grids `V{1,2}_leica_v30mm_udf_v50mm.bin`. D1(B) with each sequence's own GT file (harness), L = 2 m; `refine_T_WL: false`.
- **Methods:** M1 (VIO only; map-frame via offline D1(B)), M2 (point-to-plane, unchanged), M3 (distance field, heuristic information; `online_registration_m3.py`). M1 is rerun on this build; earlier M1 numbers stay historical.
- **Runs:** 10 per method per sequence (120 runs), rounds r01–r10; within a round, per sequence in the order above, M1 → M2 → M3. `rosbag play` rate 1.0, machine otherwise idle (no other ROS session; the user does not start ROS during the batch), frame-event log on, Phase 6 event dumps on for M2/M3. Driver: `analysis/run_phase9.sh batch`.
- **Failures (pre-registered reset rule, extended with harness checks):** a run is a failure for its method if (1) the harness marks it FAILED or it did not finish (node died, external ROS session, abort), (2) SVO performs any full reset, (3) no map-frame ATE can be computed, or (4) for M2/M3 the online D1 alignment did not fire. Failures are counted per method and sequence with reasons and excluded from ATE / RPE / drift statistics. **No run is repeated** (the driver refuses existing run ids). Exception, to be reported if it occurs: a run invalidated by an external ROS session (harness "registered with same name") is reported to the user at the gate; any re-run is the user's decision.
- **Primary metrics:** map-frame ATE (RMSE, no alignment, samples after the D1(B) window, `initial_alignment.py`) and 4-DoF ATE (RMSE, `eval_vio.py`). **Primary test:** M2 vs M3 per sequence, Welch's t-test (two-sided) on each metric, Holm correction across the 4 sequences (one family of 4 per metric), α = 0.05; reported with the mean difference M3 − M2 and its Welch 95 % CI.
- **Secondary (exploratory, uncorrected, labelled as such):** M1 vs M2 and M1 vs M3 (both ATEs), relative displacement error (mean over the RPE segment lengths), registration counts (published, dropped by queue, accepted, rejected, added) M2 vs M3.
- **Logged per run** (`analysis/phase9_run_metrics.py`): clouds published / dropped by queue / accepted / rejected / added (phase6_events); registration callback time per KF (median, p90) and latency per accepted KF = svo_node receipt of the registered pose − rosbag-record receipt of the keyframe cloud (median, p90); CPU of svo_node and of the registration node (% of one core, 1 Hz); real-time factors: playback (play wall time / bag duration), frontend (mean frame time / 50 ms), registration load (Σ callback time / bag duration); frames dropped by SVO; online-vs-offline D1 yaw.
- **Queue-drop flag (pre-registered threshold):** a sequence is flagged at the gate if M2's mean dropped/published fraction is > 2× M3's **and** ≥ 5 %. A flag triggers the Phase 10 variant "M2 with a persistent KD-tree", to separate implementation from algorithm.
- **Aggregation:** `analysis/phase9_aggregate.py` → `runs/phase9/aggregate.json`, `table.md` (mean ± sample std over non-failed runs). Each run is appended to runs/RUNLOG.md.
- **Order:** one M3 smoke run on V1_01 (`run_phase9.sh smoke`, not part of the statistics) → user check in RViz → full batch → Phase 9 gate.
